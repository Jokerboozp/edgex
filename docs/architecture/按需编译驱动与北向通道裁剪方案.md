# edgeCore 按需编译（南向驱动 / 北向通道裁剪）方案

> 目标：把「南向采集驱动」与「北向上报通道」从主二进制中变成可编译期选择的模块，
> 而 **ScanEngine 调度内核、ShadowCore 影子设备、基于影子的边缘计算（规则/虚拟设备/动作）**
> 作为不可裁剪的核心常驻。
>
> 本文所有体积数据均在本仓库实测（`GOOS=linux GOARCH=amd64 CGO_ENABLED=0`，`-trimpath -ldflags "-s -w"`），
> 测量方法见附录 A，可复现。

---

## 0. 结论先行

| 问题 | 结论 |
|------|------|
| 技术上能不能做 | 能。南向已经是 `init()` 注册表模式，**零重构即可裁剪**；北向是硬编码类型化 map，需要先做接口化重构（约 1365 行 + server 层联动） |
| 值不值得做 | 只裁南向：全量 → 单协议可省 **0.3～1.1 MiB/驱动**，13 个驱动合计净省 **2.9 MiB（10.6%）**；再把北向 OPC UA Server 也裁掉，预计单体再省 **2.5～3.5 MiB**，典型现场固件落到 **22～25 MiB** |
| 最大单项 | 南向 `opc-ua`（+1.02 MiB）、北向 `OPC UA Server`（awcullen/opcua 栈，估算 2.5～3.5 MiB）、`BACnet`（+0.38 MiB） |
| 推荐机制 | **Go build tag（编译期）+ 能力清单（运行期自描述）**，不用 `plugin`、不用子进程 |
| 推荐节奏 | 分四期：P0 南向（低风险，先拿收益）→ P1 能力清单与 UI 动态化 → P2 北向接口化（收益最大，改动也最大）→ P3 增值模块与发布矩阵 |

## 1. 现状盘点

### 1.1 构建链路

```
cmd/main.go
  ├── _ "internal/driver/{bacnet,dlt645,ethercat,ethernetip,ice104,knxnetip,
  │                      mitsubishi,modbus,omron,opcua,profinetio,s7,snmp}"   ← 空导入触发 init() 注册
  └── internal/core
        └── northbound_manager.go  ← 直接 import 7 个 northbound 实现包（硬依赖）
```

- 南向：`internal/driver/interface.go` 提供 `RegisterDriver(name, Factory)` / `GetDriver(name)`，
  13 个协议共注册 **17 个协议名**（modbus 一个包注册 6 个变体）。
  **核心层只依赖 `driver.Driver` 接口，与具体驱动包零耦合。**
- 北向：`internal/core/northbound_manager.go` 用 7 个类型化 map
  （`mqttClients` / `httpClients` / `opcuaServers` / `sparkplugClients` / `edgeOSMQTTClients` /
  `edgeOSNATSClients` / `bacnetServers`）持有实例，每个类型一套 CRUD、状态、写入历史方法；
  `internal/server/server.go` 也直接引用 `northbound/opcua`。
  **核心层与北向实现强耦合，这是裁剪的唯一硬阻塞。**

### 1.2 体积基线（实测）

| 构建 | 字节 | MiB |
|------|------|-----|
| 当前主干全量（13 驱动 + 7 北向） | 28,741,794 | 27.41 |
| 发布件 v0.1.2（dist，同配置） | 28,721,314 | 27.39 |
| **零南向驱动的核心基线** | **25,682,082** | **24.49** |
| Go 运行时下限（空 main） | 1,196,194 | 1.14 |

即：**13 个南向驱动合计只占 2.92 MiB（10.6%）**，剩下 89% 是 Go 运行时 + 核心层 + 北向 + 第三方基础库。

### 1.3 逐驱动增量（实测，相对零驱动基线）

| 驱动 | 协议名 | 增量 (KiB) | 主要第三方依赖 |
|------|--------|-----------|----------------|
| opcua | `opc-ua` | **1044** | gopcua/opcua（自带 crypto/x509 体系） |
| bacnet | `bacnet-ip` | 392 | anviod/bacnet |
| modbus | `modbus-tcp` / `modbus-rtu` / `modbus-rtu-over-tcp` / 三个 `-simple` | 328 | simonvetter/modbus |
| snmp | `snmp` | 284 | gosnmp |
| ethernetip | `ethernet-ip` | 244 | anviod/ethernet-ip |
| s7 | `s7` | 244 | anviod/gos7 |
| ethercat | `ethercat` | 216 | anviod/EtherCAT |
| omron | `omron-fins` | 188 | anviod/fins |
| dlt645 | `dlt645` | 124 | goburrow/serial |
| knxnetip | `knxnet-ip` | 124 | 无（自实现） |
| profinetio | `profinet-io` | 124 | 无（自实现） |
| mitsubishi | `mitsubishi-slmp` | 64 | 无（自实现） |
| ice104 | `iec60870-5-104` | 44 | thinkgos/go-iecp5 |

> 单驱动增量之和 3.44 MiB > 净增量 2.92 MiB，差值来自共享的 `internal/driver` 抽象层与 stdlib。

### 1.4 北向现状与估算

| 北向通道 | 自身符号 (B) | 独占依赖 | 预计可省 |
|----------|-------------|---------|---------|
| OPC UA Server | 58,289 | awcullen/opcua **3,741,305** | **2.5～3.5 MiB（最大单项）** |
| edgeOS(MQTT) | 92,293 | paho + gopsutil | 0.3～0.5 MiB |
| edgeOS(NATS) | 89,111 | nats.go | 0.8～1.5 MiB |
| MQTT | 43,659 | paho（与 edgeOS 共享） | 与上面合并计 |
| HTTP | 20,479 | 无（net/http） | ≈0 |
| BACnet Server | 16,529 | anviod/bacnet（与南向共享） | 与南向合并计 |
| SparkplugB | 16,466 | paho | ≈0（与 MQTT 共享） |

北向数字为**估算**（依赖闭包法 + 符号统计，见附录 A），因当前强耦合无法直接做 A/B 编译；
P2 重构完成后用同一套脚本实测替换。

### 1.5 三个必须解决的阻塞点

1. **北向硬依赖**：`core` → `northbound/*` 的类型化 map，不重构则 `-tags` 只能砍南向。
2. **能力清单散落**：协议枚举写死在 `internal/server/mcp_handler.go`（`Enum: [...]`）、
   UI 的 `protocolLabel.js` / `channelDefaultConfig.js` / `AiWorkbenchProtocol.vue`。
   裁剪后若不同步，会出现「UI 能建、驱动不存在」的哑巴错误。
3. **历史配置兜底**：`data/config.db` 里已存在某协议的通道，刷入不含该驱动的固件后如何处理，
   必须有明确语义（见 5.5）。

## 2. 分层模型与裁剪边界

| 层 | 模块 | 位置 | 可否裁剪 | 说明 |
|----|------|------|---------|------|
| **L0 内核（不可裁）** | ScanEngine 采集调度（EDF/冷却降级/并发限流） | `core/scan_engine.go` | ✗ | 产品核心 |
| | ShadowCore 影子设备（快照、COW、订阅、环形缓冲） | `core/shadow_core.go`、`shadow_ingress.go`、`shadow_cow.go` | ✗ | 真实设备快照，用户明确要求常驻 |
| | 边缘计算（expr 规则、窗口聚合、动作、工作流） | `core/edge_compute_manager.go`、`edge_rule_scheduler.go` | ✗ | 依赖 expr（418 KB），体积不大 |
| | 虚拟影子设备引擎 | `core/virtual_shadow_engine.go`、`virtual_shadow_manager.go` | ✗ | 影子之上的纯计算层 |
| | ChannelManager / 连接管理 / 熔断器 / RTT / MTU / Gap 优化 | `core/*` | ✗ | 协议无关的通用机制 |
| | DataPipeline / 存储（bbolt）/ Web 控制台 | `core/pipeline.go`、`storage`、`server` | ✗ | 运维入口 |
| **L1 南向（可裁）** | 13 个驱动包 | `internal/driver/*` | ✓ | P0 即可裁剪，见 5.2 |
| **L2 北向（可裁）** | 7 类上报通道 | `internal/northbound/*` | ✓（需 P2 重构） | 见 5.3 |
| **L3 增值（可裁）** | MCP 工具层 | `internal/mcp`、`server/mcp_handler.go` | ✓ | 符号 26 KB，但协议枚举要动态化 |
| | AI Agent | `internal/ai_agent`、`server/ai_handler.go` | ✓ | 43 KB |
| | EAN 群控（capability） | `internal/capability` | ✓ | 76 KB，被 edgeOS 通道与 MCP 依赖 |
| | LDAP 认证 | `server/ldap_auth.go`（go-ldap 59 KB） | ✓ | 多数现场不用 |
| | OTA 更新 | `internal/update` | ✓ | 29 KB |

L0 全部加起来符号约 594 KB（core）+ 485 KB（server）+ 运行时，是「最小可用网关」的固定成本，
再往下砍只能砍 Go 运行时和第三方基础库，性价比很低，不建议。

## 3. 候选方案对比

| 方案 | 体积收益 | 改动量 | 风险 | 结论 |
|------|---------|--------|------|------|
| **A. Go build tag（编译期）** | 高（死代码不链接） | 小（南向）/ 中（北向重构） | 低；tag 组合需收敛 | **推荐** |
| B. 生成器产出 `zz_modules.go` + 单一 tag | 同 A | 小 | 低；多一个生成步骤与 .gitignore | **推荐作为 A 的封装** |
| C. `go plugin`（.so 动态加载） | 高 | 中 | **高**：必须 CGO、`GOOS/GOARCH/Go 版本/glibc 版本`全一致才加载成功，ARM 交叉编译与现场升级基本不可维护；且无法静态链接、启动依赖文件系统 | 不推荐 |
| D. 驱动拆子进程 + IPC | 高（进程独立） | 大 | 高：进程生命周期、IPC 协议、数据拷贝、故障隔离与观测都要重做 | 不推荐 |
| E. 仅 `-s -w` / UPX 压缩 | 中（UPX 约 -50%） | 极小 | UPX 会拖慢启动、增加 RSS 峰值、部分环境被杀软误报 | 可选补充，不替代裁剪 |

**选型：A + B。** build tag 提供机制，生成器提供「写一行 `DRIVERS=modbus,s7`」的工程体验，
两者共用同一份模块清单，不冲突。

## 4. 机制设计：build tag 三态约定

### 4.1 命名

```
drv_custom  drv_modbus  drv_s7  ... drv_all        # 南向
nb_custom   nb_mqtt     nb_http ... nb_all         # 北向（P2 后生效）
feat_ai     feat_mcp    feat_ean  feat_ldap  feat_ota
```

### 4.2 三态规则（保证默认构建行为不变）

```go
// internal/driver/registry/registry.go
// Package registry 聚合所有南向驱动的空导入，是 cmd 唯一的驱动入口。
package registry

// internal/driver/registry/modbus.go
//go:build drv_modbus || drv_all || !drv_custom

package registry

import _ "github.com/anviod/edgeCore/internal/driver/modbus"
```

- **未指定任何 tag** → `!drv_custom` 成立 → **全量**（与今天完全一致，`make build`、CI、goreleaser 不受影响）
- `-tags drv_custom,drv_modbus,drv_s7` → 只有 modbus + s7
- `-tags drv_all` → 显式全量（生成器输出）

**关键设计：tag 只打在 `registry` 的导入文件上，不打在驱动包自身。**
这样 `go vet ./...` / `go test ./...` 永远编译全部驱动代码，裁剪只发生在链接阶段，
不会因为 tag 漏掉而让某个驱动悄悄腐烂。

### 4.3 生成器（可选便利层）

```
go run ./scripts/genmodules -drivers=modbus,s7 -northbound=mqtt,http
  → 生成 cmd/zz_modules.go（//go:build drv_custom + 精确 import 列表，纳入 .gitignore）
  → 打印建议的 -tags 与产物名
```

Makefile：

```makefile
DRIVERS    ?= all
NORTHBOUND ?= all
PROFILE    ?= $(DRIVERS)-$(NORTHBOUND)

.PHONY: build-profile
build-profile:
	go run ./scripts/genmodules -drivers=$(DRIVERS) -northbound=$(NORTHBOUND)
	go build -trimpath -tags "drv_custom,nb_custom" -o dist/edgeCore-$(PROFILE) ./cmd/
```

## 5. 详细设计

### 5.1 cmd/main.go 改造

删除 13 行 `_ "internal/driver/xxx"`，改为一行：

```go
import _ "github.com/anviod/edgeCore/internal/driver/registry"
```

（P2 后再加 `_ "github.com/anviod/edgeCore/internal/northbound/registry"`。
`test/test_bacnet`、`test/test_scan_objects`、`test/test_opcua_scan` 等调试入口
直接 import 具体驱动包，不受影响。）

### 5.2 南向：registry 聚合包

```
internal/driver/registry/
├── registry.go          # 空包，文档说明
├── modbus.go            # //go:build drv_modbus || drv_all || !drv_custom
├── s7.go
├── opcua.go
└── ...（每个驱动一个文件）
```

配套给 `driver` 包补两个查询函数（供能力清单使用）：

```go
// internal/driver/interface.go
func Registered() []string   // 已注册协议名，排序返回
func Has(name string) bool
```

### 5.3 北向：接口化重构（P2，改动最大但收益最大）

新增 `internal/northbound/api.go`，定义核心层唯一认识的抽象：

```go
type Deps struct {
    SB       model.SouthboundManager
    Storage  *storage.Storage
    VSM      VirtualShadowLister   // 供 OPC UA / BACnet Server 列举虚拟影子
    CM       *ChannelManager
    Pipeline *DataPipeline
}

type Connector interface {
    ID() string
    Type() string                                  // "mqtt" / "http" / "opcua-server" / ...
    Start(ctx context.Context) error
    Stop() error
    UpdateConfig(raw json.RawMessage) error
    Publish(v model.Value)
    PublishDeviceStatus(deviceID string, status int)
    Status() int
}

type Factory func(id, name string, raw json.RawMessage, d Deps) (Connector, error)

func Register(typ string, f Factory)
func New(typ string, id, name string, raw json.RawMessage, d Deps) (Connector, error)
func Types() []string
```

`NorthboundManager` 改为统一持有：

```go
type NorthboundManager struct {
    conns   map[string]api.Connector            // key = 实例 ID
    defs    map[string]model.NBEnvelope         // {ID, Type, Name, Enable, Config json.RawMessage}
    // ... 其余字段不变
}
```

原有 7 套 CRUD 收敛为一套通用流程（`Upsert/Delete/GetStats/Start/Stop/UpdateConfig`），
类型特有能力通过可选接口暴露：

```go
type Writer interface{ Write(...) error }                  // OPC UA / BACnet Server
type MetaPublisher interface{ PublishPointsMetadata() error } // edgeOS 系列
type RawPusher interface{ PublishRaw(topic string, b []byte) error } // MQTT
```

**迁移映射（现有 → 新）**

| 现有方法 | 去向 |
|---------|------|
| `UpsertMQTTConfig` / `UpsertSparkplugBConfig` / `UpsertOPCUAConfig` / `UpsertBACnetServerConfig` / `UpsertEdgeOS*` | → 统一 `UpsertNBChannel(env model.NBEnvelope)` |
| `GetOPCUAStats` / `GetMQTTStats` / `GetBACnetServerStats` | → `GetStats(id)`，返回值改 `map[string]any` 或由 connector 自带 `Stats() any` |
| `WriteOPCUA` / `BatchWriteOPCUA` / `GetOPCUAWriteHistory` | → `Writer` 可选接口 + 类型断言 |
| `SyncOPCUAServer` / `SyncBACnetServer` / `Rebuild*` | → `Syncer` 可选接口 |
| `server.go` 里 `northbound/opcua` 直接引用（证书校验、sync、write、stats 四个 handler） | → 经 `NorthboundManager` 的可选接口转发，或返回「能力未编译」 |
| `model.NorthboundConfig` 的 7 个强类型 slice | → 保留结构体做兼容解析，内部统一为 `[]NBEnvelope`；存储格式不变，避免数据迁移 |

> 兼容策略：`model.NorthboundConfig` 的 JSON/YAML 结构保持现状，
> 在 `NormalizeNorthboundForSave` 层做类型化 ↔ Envelope 互转，老配置文件不用改。

### 5.4 能力清单（运行期自描述）

```go
// internal/buildinfo/capabilities.go
type Capabilities struct {
    Version    string   `json:"version"`
    Profile    string   `json:"profile"`      // "custom" / "all" / 行业包名
    Drivers    []string `json:"drivers"`      // driver.Registered()
    Northbound []string `json:"northbound"`   // northbound.Types()
    Features   []string `json:"features"`     // mcp / ai / ean / ldap / ota
}
```

- 启动日志打印一次：`capabilities: drivers=[modbus-tcp,s7] northbound=[mqtt,http] features=[mcp]`
- `GET /api/v1/capabilities` 供 UI 与 MCP 消费
- **UI 联动**：协议下拉框、`channelDefaultConfig.js`、`AiWorkbenchProtocol.vue` 全部改为按该接口过滤，
  不再写死枚举
- **MCP 联动**：`mcp_handler.go` 里创建通道工具的 `Enum` 由能力清单动态生成，避免 AI 建出不存在的协议

### 5.5 未编译驱动的运行时语义（必须明确）

| 场景 | 行为 |
|------|------|
| 启动加载历史配置时遇到未编译协议 | 打 WARN：`channel[ch-3] protocol=bacnet-ip 未包含在当前固件，已跳过`；通道状态置 `NotCompiled`；**不阻断启动**，其它通道正常采集 |
| 运行期通过 API/MCP 创建未编译协议的通道 | 400，错误信息带已编译清单：``protocol bacnet-ip not compiled in this build (available: modbus-tcp, s7)`` |
| 北向同理 | 配置保留但不启动，控制台显示「未编译」灰标，不反复重连打日志 |
| 刷入新固件后驱动回来了 | 通道自动恢复，`NotCompiled` → 正常调度，无需改配置 |

### 5.6 构建与发布

**不要做 2^13 个 SKU。** 收敛为固定 profile：

| profile | 南向 | 北向 | 场景 |
|---------|------|------|------|
| `full` | 全部 | 全部 | 开发、演示、POC |
| `minimal` | modbus | mqtt, http | 极简数据透传 |
| `power` | modbus, dlt645, ice104 | mqtt, http | 电力/能源 |
| `building` | bacnet, knxnet-ip, modbus | mqtt, http | 楼控 |
| `factory` | modbus, s7, opc-ua, ethernet-ip, profinet-io, mitsubishi-slmp, omron-fins | mqtt, sparkplug-b | 离散制造 |

goreleaser 用多个 `builds.id` + `tags` 表达；产物名 `edgeCore-<version>-<os>-<arch>-<profile>`。
每个产物在 `about` 页与 `/api/v1/capabilities` 都能自报家门，避免现场刷错固件。

### 5.7 测试与 CI

| 阶段 | 内容 |
|------|------|
| PR | 不变：默认全量 tag 跑 `make vet` + `make test-short`（全量编译保证所有驱动代码仍然健康） |
| PR 附加 | `minimal` profile 的 `go build` 冒烟（10 秒级） |
| nightly | 每个 profile 各跑一次 build smoke + 单协议集成用例（modbus / bacnet / s7 各一个） |
| 不需要 | 13×7 全组合测试；改为「每驱动单独 build 冒烟」（`-tags drv_custom,drv_X`，只编译不跑测试，约 13×15s） |

## 6. 收益测算（典型组合）

以当前主干实测基线外推（`minimal` 等含北向裁剪的为估算）：

| 组合 | 预计体积 | 相对全量 |
|------|---------|---------|
| 全量（现状） | 27.41 MiB | — |
| 零南向驱动（仅北向裁剪前） | 24.49 MiB | −2.92 MiB |
| modbus + mqtt/http（南向裁剪，北向未动） | ≈24.8 MiB | −2.6 MiB |
| modbus + s7 + mqtt/http | ≈25.1 MiB | −2.3 MiB |
| modbus + mqtt/http + 裁 OPC UA Server/NATS/Sparkplug（P2 后） | ≈21～22 MiB | **−5～6 MiB（约 −20%）** |

单看百分比不算惊艳，但对以下场景是硬指标：

- ARMv7 / 低配网关的 **闪存占用与 OTA 流量**（差分升级时每 MiB 都是钱）
- **常驻 RSS**（未链接的代码不占内存页）
- **攻击面与合规**：不用的协议栈（OPC UA 的 X.509/ASN.1、SNMP、LDAP）不进固件，CVE 暴露面直接归零
- **启动时间**：包初始化与 `init()` 注册减少

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 现场刷错 profile 固件，通道全灰 | 高 | 文件名带 profile；`/api/v1/capabilities` 自描述；关于页展示；升级工具校验当前配置所用协议 ⊆ 固件能力，不匹配则拒绝并提示 |

| UI 枚举与固件能力不一致 | 中 | P1 就把 UI 改为能力驱动，不依赖 P2 完成 |

## 附录 A：测量方法（可复现）

环境：`go1.26.4 windows/amd64`，交叉编译 `GOOS=linux GOARCH=amd64 CGO_ENABLED=0`，
链接参数 `-trimpath -ldflags "-s -w"`（与 `.goreleaser.yml` 一致）。

**A1. 逐驱动增量（实测，表 1.3）**

```bash
# 1) 复制 cmd/main.go 为探针，按注释保留/删除驱动的空导入行
# 2) 零驱动基线
go build -trimpath -ldflags "-s -w" -o none.elf    probe_none/main.go
# 3) 每个驱动单独一个探针
go build -trimpath -ldflags "-s -w" -o modbus.elf  probe_modbus/main.go
# 4) 差值即该驱动净增量
```

**A2. 符号归属（表 1.4 的估算依据）**

```bash
go build -trimpath -o full.elf ./cmd/            # 注意：不加 -s -w
go tool nm -size full.elf | awk '{...聚合到包...}'
```

`dist/` 下的发布二进制是 `-s -w` 过的，`go tool nm` 读不出符号，必须自己编一版未 strip 的。

**A3. 依赖闭包法（交叉验证）**

```bash
# 空 main 基线 vs 空 main + 单个 northbound 包，测该包及其传递依赖的增量
```

该方法会把 stdlib 共享部分重复计入，绝对值偏大，只用于排序与量级判断；
表 1.4 的北向数字是「符号统计（主） + 闭包法（校验）」综合后的区间估计，
P2 重构完成后替换成 A1 同款实测值。

## 附录 B：待确认

1. **是否接受多 SKU 运维成本**？若不接受，可只发布 `full` 与 `minimal` 两个，其余按需定制编译（不下发到 release）。
2. **北向 OPC UA Server 是否为必留**？它是最大单项，若多数现场必须，P2 的收益会打折，需先确认产品策略。
3. **`feat_mcp` 是否可裁**？MCP 是论文里定位的 AI Native 扩展层，裁掉会影响对外叙事，建议默认保留、允许定制时关闭。
4. **是否需要 `CGO_ENABLED=0` 之外的约束**？例如某些现场要求静态链接 musl，会与 build tag 组合交叉影响编译矩阵。
